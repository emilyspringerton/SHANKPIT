# PELLEGRINO phone browser (SHANKPIT-PELLEGRINO-APP-02) — status + handoff

**Read this before touching anything PELLEGRINO/phone-related.** Written 2026-10-16 for the next
Claude session picking this up — what happened, what's real/verified, what's still open.

## Why this exists

The founder asked for a "PELLEGRINO phone app" that functions as a real browser inside SHANKPIT's
zombies mode. A prior session (`SHANKPIT-PELLEGRINO-APP-01`, `EMILY/BACKLOG.md` SECTION 624) satisfied
the words in the wrong place: it added a `PELLEGRINO` tile to `apps/lobby`'s top-level **Apps launcher
page** (`AppsAction` enum — DEADWEIGHT/PITVIPER/IDUNA/REDGARDEN/EDITOR/ZOMBIES/PELLEGRINO), which spawns
the real PELLEGRINO binary as a **separate child-process window**. That tile never appears inside an
actual zombies match — it's a main-menu launcher, not the in-fiction phone. The founder confirmed
(mid-conversation) they want the real thing: a browser tile visible when you open your phone *during*
a zombies match, rendered inside the phone panel, with real networking (TLS, HTTP/3) — not a popped-up
window, not a mockup.

This session (SHANKPIT-PELLEGRINO-APP-02) built that. It is NOT done — see "What's left" below.

## What actually shipped (3 repos, verified individually)

**PELLEGRINO** (`b8a421a`) — `pellegrino.prn` gained a second embed surface, `embed-nav-*`
(`embed-nav-open/-start/-step/-click/-wheel/-key/-text`), alongside the existing `embed-*` API (which
is static/host-fed and **never navigates** — that one is `packages/pellegrino_embed`'s OS-menu skin,
leave it alone). `embed-nav-*` reuses PELLEGRINO's real navigation machinery as-is: `start-nav` /
`nav-dispatch` for dispatch, and `frame-loop`'s own per-frame pump sequence (`pump-h3`, `pump-net`,
`css-pump`, `img-pump`, `pump-static`) for the non-blocking step. No TLS/QUIC logic was written — it
was already there and proven; this just exposes it as library calls instead of CLI-only.

Also fixed, in the same commit: several pre-existing `do(...)` **C-emission bugs** in the current
PARENA compiler (a `do` used for its value inside a `cond`/`if` arm emits literally as invalid C
`do(...)`) — hit compiling `pellegrino.prn` with the full HTTP/3/QUIC stdlib linked in, unrelated to
the new code. Fixed the documented way (`PELLEGRINO/CLAUDE.md`'s own VS0-quirks list): extract into a
named helper fn. Functions touched: `do-newline`, `calc-prod-rest`, `calc-sum-rest`, `ua-style`,
`var-put`, `note-page-bg`, `fm-send`, `on-key-field`. **If you hit another `? do(` compile error
anywhere in `pellegrino.prn` or PARENA stdlib, this is the same bug — same fix, don't investigate from
scratch.**

**PARENA** (`f7771b7`) — same bug, same fix, in `stdlib/net/quic_client.prn`'s `quic-pump`
(`qcn-complete-fail!` helper extracted).

**SHANKPIT** (`89437ec`) —
- `packages/common/phone.h`: `BP_APP_PELLEGRINO` added to the `BpApp` enum + `BP_APP_NAMES`. No new
  `BpEffectKind` — the host special-cases `app == BP_APP_PELLEGRINO` directly, same precedent
  `BP_APP_GFD`'s text terminal already set (phone.h stays network-free by design).
- `packages/pellegrino_browser_embed/` — new package, sibling to `packages/pellegrino_embed` (which
  stays untouched and still does the no-network OS-menu skin). Generated by the new
  `scripts/gen_pellegrino_browser_embed.sh` from `../PELLEGRINO` + `../PARENA`, pulling in the
  HTTP/3/QUIC stdlib (`net/quic_wire`, `net/h3_wire`, `crypto/quic_crypto`, `net/quic_tls`,
  `net/quic_client`) and renaming every engine/runtime global to `pgb_<name>` (vs.
  `pellegrino_embed`'s `pgm_<name>`) so both can link into one `apps/lobby` binary — checked with `nm`,
  zero collisions across `pellegrino_embed`, `pellegrino_browser_embed`, and
  `packages/world/parena_runtime.c`. `phone_browser_embed.c/h` is the thin C wrapper around
  `embed-nav-*`; `phone_browser_gl.h` is the GL glue (one textured quad, same pattern
  `packages/pellegrino_embed/os_menu_gl.h` already established for the OS menu — also still unwired,
  pre-existing gap, not this session's doing).
- `apps/lobby/src/main.c`: `draw_phone_app` renders the live browser via `pbg_draw()` when
  `app == BP_APP_PELLEGRINO`; input routing forwards `SDL_TEXTINPUT` and every keydown to
  `phone_browser_text`/`phone_browser_key` while this app is open (mirrors the existing
  `BP_APP_GFD` special-case) — only a real "quit" result from PELLEGRINO's own `on-key` (Esc/q
  outside any text-entry/form-field mode) closes the app and returns to the phone's home grid.

## What's left (real, named, not done)

1. **No BUILD.bazel or Makefile wiring for `packages/pellegrino_browser_embed` yet.** The package
   exists and compiles standalone (verified above), but nothing in `SHANKPIT/Makefile`'s `LOBBY_SRC`
   or a `BUILD.bazel` actually builds+links it into the real `lobby`/`shankpit` binary yet. Follow
   the `EDITOR_GAME_OBJS` pattern already in `Makefile` (lines ~70-120): this needs its own
   pre-built-object-then-linked-at-the-end treatment (NOT added to the shared `LOBBY_SRC` gcc
   invocation — it needs its own TLS/mbedTLS copts and include paths that the rest of `LOBBY_SRC`
   must never see). You'll need: mbedTLS objects (109 of them, build each `library/*.c` with
   `-DMBEDTLS_USER_CONFIG_FILE="pellegrino_user_config.h"` + `-I<mbedtls>/include` +
   `-I<mbedtls>/library` + `-Ipackages/pellegrino_browser_embed/runtime`), one monocypher object, one
   `phone_browser_embed.o` (same flags, see `scripts/gen_pellegrino_browser_embed.sh`'s own probe-step
   invocation for the exact flag set), then link all of that alongside the rest of `LOBBY_SRC`.
2. **A real `make lobby` full link was never attempted on this box** — pre-existing, unrelated gap:
   there's no `../EDITOR.GAME` sibling checkout here, which `apps/lobby/src/editor_widget_bridge.c`
   needs (same blocker `SHANKPIT-PELLEGRINO-APP-01` already hit). Get `EDITOR.GAME` checked out
   alongside, or verify this package's wiring some other way (e.g. a standalone test binary linking
   just `LOBBY_SRC` minus the editor bridge, if that's even feasible) before trusting a full build.
3. **No live in-game screenshot.** Nobody has actually seen this render inside a running
   `MODE_ZOMBIES` match yet. Once `make lobby` links, verify under Xvfb: open the phone, select
   PELLEGRINO, confirm a real page renders in the panel, type a URL in the address bar, confirm real
   navigation, confirm Esc backs out to the home grid without closing the whole phone unexpectedly.
4. **No mouse-click wiring.** The phone's own input model has no existing mouse-click precedent
   anywhere to extend (checked directly — it's entirely keyboard/gamepad-cursor driven today), so
   browsing is keyboard-only: `:`-style typing happens automatically via address-bar focus,
   Tab/Shift+Tab selects links, Enter/Space activates, arrows scroll. This is an honest, scoped
   v1 limit, not an oversight — decide if mouse support is actually wanted before building it (it's
   a bigger lift: SHANKPIT runs relative mouse-look for the FPS camera while playing, so capturing an
   absolute cursor position over just the phone panel needs its own mode-switch, same category of
   problem the game's existing menu/cursor system presumably already solved once — check how existing
   phone navigation reconciles with mouselook, if at all, before inventing a second mechanism).
5. **CI/release wiring not touched.** `release.yml`'s cross-compile/bundle list doesn't know about
   this package either (same named-but-undone gap `SHANKPIT-PELLEGRINO-APP-01` left for its own
   lobby-launcher tile).
6. **`README.md` / `CHANGELOG.md` not updated.** Per this repo's own "README Reality" rule, do this
   once the build actually links — don't claim it works in the README before `make lobby` proves it.
7. **No Apple filed, no `[x]` in `EMILY/BACKLOG.md` yet.** This doc is the handoff; the actual
   backlog entry (added this session, see SECTION 625 below) is still open/unchecked. File the Apple
   and check it off only once items 1-3 above are real.

## Quick orientation for whoever picks this up

- `PELLEGRINO/pellegrino.prn` lines ~5285-5420-ish: `embed-*` (old, static, OS-menu) then
  `embed-nav-*` (new, this work) — read both doc comments, they explain the real difference.
- `packages/pellegrino_embed/` = OS-menu skin, no network, **do not touch for this feature**.
- `packages/pellegrino_browser_embed/` = this feature. `scripts/gen_pellegrino_browser_embed.sh`
  regenerates it from sibling `../PELLEGRINO`/`../PARENA` checkouts — rerun it after any
  `embed-nav-*` change in PELLEGRINO.
- The `pgm_`/`pgb_` rename split exists ONLY because both packages link into the same `apps/lobby`
  binary. If you ever add a THIRD embedded-PARENA-engine package into that same binary, it needs its
  own third prefix, checked the same way (`nm -g --defined-only` on all pairs, diff for overlap).
