# shankpit-460 on Android

v1 is the **existing WebAssembly build in a WebView** — the same module WOTAN serves
at `/shankpit-460/`, compiled from PARENA. There is no Android port of the C engine
in here on purpose: the wasm has zero imports and renders into its own 640×360
framebuffer, so the entire platform layer is a WebView plus touch controls.

```
android/
  app/                       Gradle module (plain framework WebView, no AndroidX)
    src/main/java/.../MainActivity.java   serves the bundle from https://shankpit.local
  tools/verify-web-bundle.mjs             headless check: wasm + touch pad + offline path
../apps/shankpit-460/                    the game itself (packaged verbatim into assets)
  index.html                 Android-first page: no fonts, no nav, no server CSS
  sp-host.js                 generated by `parena build` -- never edited by hand
  shankpit460.wasm           the game
  android-controls.js        virtual gamepad + offline matchmaking shim + drag-to-aim
```

## Build

```bash
# needs JDK 17+, Android SDK (platform 34, build-tools 34.0.0), Gradle 8.7
cd android
gradle assembleRelease      # -> app/build/outputs/apk/release/app-release.apk
```

CI does exactly this in `release.yml`, and the APK ships as
`ShankPit_Android_<build>.apk` alongside the desktop zips in the same auto-release.

Environment knobs (all optional):

| Variable | Effect |
|---|---|
| `SHANKPIT_ANDROID_VERSION_CODE` | `versionCode` (CI passes the run number) |
| `SHANKPIT_ANDROID_VERSION_NAME` | `versionName` |
| `SHANKPIT_ANDROID_BACKEND` | matchmaking base URL, e.g. `https://okemily.com` |
| `SHANKPIT_ANDROID_KEYSTORE` + `_PASSWORD`, `_KEY_ALIAS`, `_KEY_PASSWORD` | release signing |

Without a keystore the release APK is signed with the local debug key. That installs
fine by sideload (which is the point) but is not a Play upload, and because CI mints a
fresh debug key per run, updating over an installed copy needs an uninstall first.

## Matchmaking, and what happens with no backend

The web build talks to `/api/v1/shankpit460/play` (WebSocket) and
`/api/v1/shankpit460/status` on its own origin. Android keeps that contract:

- **backend set** — those relative calls are rewritten to it (`wss://` for the socket).
  The game behaves exactly as on the site.
- **no backend (default)** — an inert WebSocket is installed, so the wasm drops into
  the **local bot match** it already knows how to run and never retries a dead
  endpoint. The HUD says `Bot match (no matchmaking)` and shows an `Offline demo` chip.
  Nothing fails, nothing throws, no network is touched.

Verified headlessly, not assumed: with no backend the wasm reaches the match phase,
keeps simulating ticks, and **zero** sockets are constructed.

## Controls

The wasm takes a standard gamepad, so the touch layer overrides
`navigator.getGamepads()` with a synthetic pad. Nothing in the generated host is
patched.

Pointer lock is the exception, and it used to be a real bug. WebView offers no
Pointer Lock API, but the wasm does ask for it — `sp_wants_lock()` is 1 for the
whole match — and the host defines `lockedP()` as `document.pointerLockElement !=
null`, handing the wasm `sp_lock(1)` only from its `pointerlockchange` listener.
With no lock that listener never fired, so the game sat behind its click-to-play
gate with FIRE dead while the pad still moved you (pad axes are polled every
frame, unconditionally). `android-controls.js` therefore presents a locked canvas
(`pointerLockElement` resolves to the canvas, `requestPointerLock` resolves,
`exitPointerLock` is a no-op) and dispatches `pointerlockchange` — before the
module runs and again at load, +250/+1000/+2500 ms and on the first tap.

| On screen | Gamepad | Action |
|---|---|---|
| left stick | axes 0/1 | move |
| drag anywhere | axes 2/3 | aim |
| FIRE | RT (7) | fire |
| JUMP | A (0) | jump / float |
| CROUCH | B (1) | crouch / slide |
| RELOAD | X (2) | reload |
| ABILITY | LT (6) | ability |
| WEAPON | RB (5) | next weapon |

The first tap starts the match (a pad button is what leaves the title screen) and is
also the gesture that unlocks audio.

## Verification

```bash
node android/tools/verify-web-bundle.mjs
```

Runs the real `.wasm` and the real `android-controls.js` in a minimal fake DOM and
asserts: bundle files and page ids, virtual pad shape, tap-starts-a-match, the sim
advancing, no socket in offline mode, status rewording, button map, and that the
module is still import-free and under 2 MB. CI runs it before `assembleRelease`.

## Unification with main SHANKPIT (started, not finished)

`apps/shankpit-460/` is now SHANKPIT's own copy of the 460 client; WOTAN's
`shankpit-460/` is downstream of it from here. What was stripped for v1 is the
marketing shell (fonts, nav, site CSS, SSO links) — the game module itself is
byte-identical to the one WOTAN serves.

Known gaps, deliberately not in v1:

- **No zombies.** The 460 arena is deathmatch-only; the zombie mode lives in the C
  lobby build and has no wasm equivalent yet.
- **No map editing.** NOCK is a C/PARENA server plus a browser editor in the desktop
  build; the Android client reads none of it.
- **No accounts.** Playing as a guest; the IDUNA SSO link is a no-op in-app.
- **Matchmaking is unused** until a backend URL is configured — there is no server
  running the `/api/v1/shankpit460/*` endpoints today.
- Touch controls are landscape-only; portrait shows a rotate prompt by design.
