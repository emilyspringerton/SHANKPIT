## Part 1: Yggdrasil Doctrine: PARENA Engineering Standard

This is the standing standard for all work on PARENA, VS0, Macau, REFLUX, and the SHANKPIT engine. It applies to every contributor, human or agent, and every session. Task briefs refer to it. They do not restate it.

Claim IDs: **INV** invariant, **BEH** behaviour, **IFC** interface, **MET** metric, **POL** policy, **NAR** narrative and rationale.

**Linked documents:** [VS0 / Macau Plugin Contract](https://claude.ai/artifact/5bCL7Y7XXscdDDAQqJANNy) · [VS0 Build Process: Claude Code Brief](https://claude.ai/artifact/1g64CDX6oJpuRYr7dqeBNP)

### 1. The three roots

The tree has three roots, in priority order. When any two conflict, the higher one wins.

#### Root I: Always PARENA first

- **INV-1.1** Decisions live in PARENA. Editing, tokenizing, language selection, layout, state transitions, command construction, and game logic are `.prn` source.
- **INV-1.2** Host code is boundary plumbing only: windowing, input events, filesystem and process syscalls, platform `#ifdef` splits. Host code makes no product decisions.
- **POL-1.3** Before writing host code, ask whether it is plumbing or a decision. A decision goes in PARENA, with a minimal FFI function underneath it.
- **IFC-1.4** Host access goes through `#target` forms with `inline-c`, and adds an `:llvm` key with `inline-llvm` wherever the signature is scalar. One form serves every backend. Never fork a file per target.
- **NAR-1.5** PARENA compiles to C, LLVM, WASM, TypeScript, and Java. Logic written in PARENA travels to every target. Logic written in host C is stranded on one target.

#### Root II: Mods first

- **INV-2.1** New features ship as mods on a published mod surface (`editor/plugin` for the editor). They are not new branches in a host `main()`.
- **INV-2.2** The core knows nothing about specific languages, games, or content. Built-in languages and built-in game systems are mods like any other.
- **IFC-2.3** Mods communicate with each other only through REFLUX. There are no direct cross-mod calls.
- **POL-2.4** If a feature can't be built as a mod, the missing piece is a gap in the mod surface. Extend the surface first, then build the feature as a mod.
- **NAR-2.5** The game is already mostly PARENA mods. The editor follows the same model, so the engine stays a platform rather than a single product.

#### Root III: API-driven development

- **POL-3.1** The order is contract, then test, then implementation. No implementation lands without a recorded contract.
- **IFC-3.2** A contract states the exported signature, its types and regions, its result shape, and its failure modes.
- **POL-3.3** Where Monaco or another reference API has an equivalent, match its names and shapes. Any divergence is recorded with its reason in the contract doc.
- **IFC-3.4** Prefer scalar signatures (`I32`, `Bool`, `Unit`). A `String`, `Result`, or struct signature carries a per-target note.
- **NAR-3.5** Contracts let parallel threads build against each other before either side is finished, which is how a fleet of agents works without colliding.

### 2. System map

- **SHANKPIT engine:** the full-stack game engine and runtime, down to the metal. It is also the host for a stripped-down PARENA-native browser. The long-range aim is a game operating system that can run on dedicated consoles.
- **PARENA:** the typed, Lisp-like systems language. It builds the world, powers the game through mods, and compiles to multiple targets. A clean-room rewrite is in progress on a separate thread, separating the game from the engine.
- **VS0:** the PARENA-native editor component. A thin SDL2 host in `examples/editor_main.c` runs over `stdlib/editor/*.prn`.
- **Macau:** the engine module that presents VS0 as the code lens into the PARENA layer. It is to the game what Monaco is to the web, with Monaco API parity as the target.
- **editor/plugin:** the editor mod surface. Currently it holds `register-command` and `get-config`.
- **REFLUX:** the cross-mod pub/sub layer. It is a shared append-only action log. Mods dispatch actions into it and poll it from host-held cursors.

### 3. REFLUX rules

- **IFC-3R.1** Dispatch: `reflux-dispatch` with an action type and three `I32` payloads.
- **IFC-3R.2** Poll: `reflux-log-size`, then `reflux-action-*-at` over the range since the mod's cursor.
- **INV-3R.3** The host holds poller cursors. PARENA makes decisions from them.
- **POL-3R.4** Every action type is registered in the shared action-type table, inside its owning subsystem's reserved range, and cross-referenced in the dispatching and polling source.
- **POL-3R.5** Payloads are scalars. Larger data is referenced by an index or handle into host-held state, never copied into the log.

### 4. Process

#### 4.1 Task loop

1. **Contract:** write or update the API in the relevant contract doc.
2. **Placement:** check PARENA versus host (Root I) and mod versus core (Root II).
3. **Test:** write the test against the contract.
4. **Implement:** keep the diff scoped to the task.
5. **Clean build:** run the full build to the warning bar in 4.3.
6. **Record:** update the contract doc, the defect list, and the file header comments.

#### 4.2 Definition of done

- **MET-4.2.1** Linux build clean at the bar in 4.3.
- **MET-4.2.2** Windows build confirmed. Windows is the test platform.
- **MET-4.2.3** Tests pass, including the Xvfb smoke target for UI paths.
- **MET-4.2.4** The contract doc reflects what shipped and what was deferred.

#### 4.3 Build bar

- **INV-4.3.1** `-std=c99 -Wall -Wextra -pedantic -Werror`, zero warnings.
- **POL-4.3.2** A broken build blocks all feature work until it is fixed.

#### 4.4 Data safety

- **INV-4.4.1** No operation writes to a path other than the file currently shown to the user.
- **INV-4.4.2** Read-only views (hex view and others) refuse to save.
- **POL-4.4.3** Any data-loss defect goes to the top of the queue, ahead of all feature work.

#### 4.5 Session intake protocol

Every working session runs intake before build: intent, scope, context, clarification, source, execution, review, record. This is the sequence that produced the editor contract, the defect list, and the Claude Code brief on 2026-11-07.

1. **Intent.** The founder states the day's goal and the threads running in parallel.
2. **Scope check.** The agent asks one or two questions to find the smallest useful slice and where to start.
3. **Context transfer.** The founder supplies knowledge that isn't in the docs yet: names, architecture, which layer owns what.
4. **Clarification.** The agent asks targeted questions only where an answer changes the design, such as which layer hosts what or how a name is spelled.
5. **Source paste.** The founder pastes the real code or headers. Messy and partial is fine.
6. **Execution.** The agent produces the contract, the review, the fixes, and the briefs.
7. **Self-review.** The agent rereads the whole session for errors, contradictions, and missed value before handoff.
8. **Record.** The agent updates and links the docs and saves durable facts.

- **POL-4.5.1** Scope questions are asked once. When the founder has set scope, the agent proceeds and embeds any remaining concern in the work instead of re-arguing it.
- **INV-4.5.2** Knowledge the founder states in a session is written into the governing docs before the session ends.
- **INV-4.5.3** Pasted source is ground truth. Where source and a doc disagree, the source wins and the doc is corrected in the same session. Example: the `plugin.prn` header listed the shell as undecided, while `editor_main.c` showed SDL2 already shipped.
- **POL-4.5.4** The agent does not interrupt mid-thought. In voice sessions it waits for the founder to finish before speaking.
- **POL-4.5.5** Names are confirmed on first use and spelled consistently afterwards (for example PARENA, not Parana).
- **MET-4.5.6** A session counts as complete when the docs are linked, the task queue is updated, and the build bar in 4.3 is the next action.

#### 4.6 The value ladder

A brief is not ready for handoff until the founder judges it worth the tokens. Scope climbs rung by rung until it reaches real value, then gets cut to the smallest first step that still delivers that value. Case study: the 2026-11-07 session, which went from a Monaco-compatible plugin interface to booting the game into BRAWLPIT.

1. **Draft.** Write the brief at the current rung.
2. **Value test.** The founder asks: would I open Claude Code and spend tokens and time on this? If the answer is no, name what is missing.
3. **Climb.** The agent proposes the next rung up as two or three player-facing options, ranked, each one building on the rung below. The founder picks one or combines them.
4. **Repeat** steps 2 and 3 until the answer is yes.
5. **Cut.** The founder cuts the scope to a first deliverable. The higher rungs become the ordered queue behind it.
6. **Frame.** State the deliverable as the product a person experiences, not as the systems underneath it.

- **POL-4.6.1** The value test is the founder's. An agent never declares a brief worth the tokens on the founder's behalf.
- **INV-4.6.2** A brief's deliverable is something a person can see or play in the running product. Plumbing appears as how, never as what.
- **POL-4.6.3** When a rung fails the value test, its work moves into the queue as an enabler of the next rung, not removed. Example: the difficulty ramp became one application of the Actor API.
- **POL-4.6.4** Each decision goes into the brief as Decided at the moment it is made. At most two open questions are put to the founder at a time.
- **POL-4.6.5** On an apparent large scope jump, the agent raises the concern once, then takes the founder's word on what already exists.
- **POL-4.6.6** Obvious software conventions, such as a shortcut being ignored while a text field has focus, are written into the brief without asking the founder.
- **POL-4.6.7** Legacy is the default assumption. A deliverable creates only the mods it needs. Every other system stays legacy until a later deliverable needs it.
- **MET-4.6.8** Handoff happens only after an explicit yes on the value test, with the first cut and its acceptance test at the top of the brief.

### 5. Conventions

- **POL-5.1** File header comments record scope, what shipped, deferred gaps, and the founder request that prompted the work, matching the existing repo style.
- **POL-5.2** Deferred work is named explicitly as deferred. A gap is never silent.
- **POL-5.3** Platform code uses the established `_WIN32` / `__APPLE__` / else split.
- **POL-5.4** Names follow the Norse and Yggdrasil register for new subsystems where a name is being chosen, except where an existing name is already established (Macau, REFLUX, VS0).
- **BEH-5.5** Failures are honest and non-fatal where possible: logged, reported, and leaving the running session intact.
